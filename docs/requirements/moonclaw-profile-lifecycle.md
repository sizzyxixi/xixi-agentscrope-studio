# MoonClaw 用户画像持续更新与智能体核心文件设计

- 版本：v0.1 评审建议
- 日期：2026-10-23
- 关联：[工作台需求与数据字典](./moonclaw-workbench.md)
- 范围：经营阶段命名、表单／对话／授权事件统一画像、USER.md 与数据库选型、通用助手与 onboarding 分工、变化感知及个性化引导。
- 本文的数据模型与事件链路为设计方案；2026-10-23 已按本方案重排智能体核心规则，见[核心文件与接入说明](../../service/personas/main/README.md)。本次未迁移生产数据、改动工具审批或接通结构化画像数据库。

## 1. 经营阶段文案建议

推荐使用：**筹备开店 → 起步经营 → 规模运营**。

| 选项 | 面向用户的解释 | 业务语义 |
| --- | --- | --- |
| 筹备开店 | 还没开店，正在选平台、找货源 | 当前经营范围内尚在筹备 |
| 起步经营 | 已开店，正在小规模试水 | 已开始开店后的上新、试卖与经营准备；不要求已有订单 |
| 规模运营 | 已有稳定业务，正在扩展规模 | 用户明确声明的稳定经营／扩张阶段；不单靠店铺数推断 |
| 随便看看 | 暂不填写，先和助手聊聊 | onboarding 的跳过动作，不是经营成熟度 |

“开店起步”可作为备选；“新手卖家”描述经验，“小规模经营”描述体量，两者都不能准确替代经营阶段。经营多年但体量小的卖家不一定属于起步阶段；大团队进入新平台也可能处于筹备阶段。

界面如仍需保留“其他”，建议展示为“其他／先聊聊”，数据上记录跳过收集，不把 other 作为永久、不可变的经营阶段。既有文档与 Demo 中的“已经开店”建议在评审通过后统一替换为“起步经营”，本文不视为文案已获最终确认。

## 2. 三个必须拆开的状态

| 状态 | 回答的问题 | 建议字段／值 | 不能等同于 |
| --- | --- | --- | --- |
| 引导状态 | 是否已经看过、完成或跳过引导 | onboarding_status：not_seen／in_progress／completed／skipped | 经营阶段、画像是否完整 |
| 画像完整度 | 已知多少字段、还缺什么 | profile_status：unknown／partial／complete；missing_fields | 是否已经引导过 |
| 经营阶段 | 在某个业务范围里经营到哪一步 | stage：unknown／preparing／early_operation／scaling | 授权状态、用户是否愿意填写表单 |

因此，“随便看看”应记录 onboarding_status=skipped；经营阶段保持 unknown，其他明确资料可以保留。用户以后补充信息，可以从 unknown 更新到 preparing，不能因曾跳过就停止收集。

表单点过“完成”也不代表所有未来需要的字段都已具备；后续刊登需要国家站点、店铺或履约信息时，仍可按任务补齐。

## 3. USER.md 与数据库：推荐分工

**数据库保存可校验、可查询的当前事实和变化历史；USER.md 是针对当前用户生成的只读摘要。共享规则文件不保存真实用户资料。**

### 3.1 方案对比

| 需求 | 仅使用每用户 USER.md | 仅数据库结构化字段 | 数据库＋USER.md 摘要 |
| --- | --- | --- | --- |
| AI 阅读画像 | 方便，需主动加载最新内容 | 运行时需要组装成上下文 | 方便，摘要由结构化数据生成 |
| 表单回填与条件必填 | 需要解析 Markdown，格式变化易出错 | 直接按字段处理 | 按数据库处理 |
| 平台／店铺筛选和推荐 | 文件扫描与解析成本高 | 可索引查询 | 数据库查询后给 AI 摘要 |
| 店铺授权事件更新 | 可做，但需额外实现文件锁、合并和来源追踪 | 可事务化、幂等化 | 先更新数据库，再刷新摘要 |
| 多端／多人并发 | 需自行实现版本、冲突和隔离 | 可用事务和版本检查 | 数据库处理并发，摘要标记版本 |
| 自由文本偏好 | 灵活 | 可用独立文本记忆或 JSON 扩展 | 结构化事实＋文本记忆共同生成摘要 |
| 追溯“为什么变了” | 需额外版本日志；仅一份当前文件不够 | 可建立字段证据和事件表 | 数据库可追溯，摘要突出最近变化 |
| 更正、忘记和停用 | 需同时清理文件、缓存与历史注入 | 可集中管理状态 | 数据库失效后重建摘要；禁止旧文件自动回灌 |
| 导出和迁移 | 便于人工阅读与携带 | 需要导出能力 | 可导出 Markdown／JSON |
| 适合范围 | 单用户、低并发、主要依赖文本交互的原型 | 平台业务系统 | 本项目推荐方案 |

这些限制不是 Markdown 文件绝对无法实现，而是最终会在文件之外重新建设事务、检索、证据、同步和权限机制。

### 3.2 主数据与同步规则

1. 结构化画像只有一个主写入入口：Profile Service。表单、会话工具与事件消费者调用同一个服务。
2. USER.md 从数据库生成，不允许 AI 一边改文件、前端另一边改字段，形成双主数据。
3. 可以不落物理文件：每轮按账号读取最新画像，生成 Markdown 或 JSON 注入运行时即可。
4. 如必须提供物理 USER.md，按账号／业务主体隔离路径，并记录 profile_revision；它是投影或导出，不是第二套事实库。
5. 用户若通过编辑摘要修改画像，应先把修改解析成字段补丁，经过同一校验服务再保存，不直接覆盖数据库全量值。
6. 摘要生成失败不能撤销已经提交的真实授权事实；下一轮按数据库版本重建，不能静默使用过期摘要。
7. 保留可扩展的文本记忆：品牌调性、沟通偏好、选品标准等不必都转成固定列；但平台、阶段、授权状态不能只存一段自由文本。

### 3.3 当前项目的实际情况

| 当前组成 | 实际用途 | 与目标方案的差距 |
| --- | --- | --- |
| service/personas/main/agents.md | 通用助手身份、工作原则与边界 | 可以继续保留 |
| service/personas/main/bootstrap.md | 首次普通对话的引导规则 | 不能承担以后每次资料变化的处理 |
| service/personas/main/user.md | 共享的用户字段与记忆规则模板 | 不是某个账号可随意改写的 USER.md |
| 账号记忆资源“MoonClaw 用户身份” | Main 使用 save_user_profile 固定名称和更新对象；通用 save_memory 仍保留 | 已有账号隔离及确认，但不是完整的结构化画像、证据和变化事件模型 |
| user_onboarding 标记 | 记录账号是否接受过首次引导 | 目前是“看过引导”的标记，不能直接代表画像完整 |
| 前端工作台画像 | 保存在浏览器本地，用于演示页面分流 | 尚未与账号记忆、授权事实和统一画像服务打通 |

当前项目存储层可按配置使用 SQLite 或 PostgreSQL；本文的数据库方案不要求更换已选择的数据库产品。生产接入重点是统一资料模型和更新路径。

## 4. 画像需要有业务范围

不能只维护一份全局 stage，再把用户最后一次提到的平台覆盖进去。例如用户在 Amazon 规模运营，同时准备新开 TikTok 店，应保留两个事实。

| 层级 | 建议内容 | 示例 |
| --- | --- | --- |
| 用户偏好 | 称呼、语言、沟通方式、跨业务的内容偏好 | 喜欢简短结论和对比表 |
| 经营主体 | 当前业务主体及归属；首期可先按账号管理 | 一个用户经营的业务 |
| 经营范围 business_context | 平台、必要时市场／站点、经营阶段、目标与类目 | Amazon／美国／规模运营；TikTok／目标站点待定／筹备 |
| 店铺事实 | 店铺 ID、所属范围、授权和可用状态 | 某 TikTok 店已连接 |
| 当前任务上下文 | 此次问题正在讨论哪个平台、目标和时间范围 | 本轮先处理 TikTok 开店 |

首期建议支持“一个账号、多平台经营范围”。市场和店铺层级按实际任务逐步细化，避免首次收集时让用户填写一份庞大的组织结构。

全局首页如果只能展示一个阶段，应展示当前选中经营范围的阶段；不能拿一个平台的状态代表用户所有生意。

## 5. 建议新增或扩展的数据对象

### 5.1 对象职责

| 对象 | 保存内容 | 作用 |
| --- | --- | --- |
| user_preferences | 用户明确提供的偏好和适用范围 | 通用助手使用 |
| seller_profile | 画像归属、状态、结构版本和整体 revision | 画像入口与版本管理 |
| seller_business_context | 每个平台／市场的阶段、目标、类目 | 支持多平台不同阶段 |
| profile_field_evidence | 字段值的来源、范围、时间与验证状态 | 解释、冲突判断、修正 |
| profile_change_candidate | 推断或冲突待处理项 | 避免把所有猜测立即写成正式事实 |
| profile_change_event | 实际提交的修改及旧新值 | AI 感知变化、前端反馈、审计 |
| commerce_shop | 平台返回的店铺与授权事实 | 授权状态的业务主数据 |
| onboarding_state | 看过、跳过、完成及当前步骤 | 避免重复弹完整问卷 |

既有记忆资源可继续保存自由文本偏好；不要求首期为每个字段单独建一张表。以上是逻辑对象，可按业务复杂度落为列、关联表和受 schema 校验的 JSON。

### 5.2 持续更新相关字段

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| owner_user_id／business_id | ID | 明确账号与经营主体归属；不能跨账号合并 |
| business_context_id | ID | 变化适用的平台／市场范围 |
| stage | enum | unknown／preparing／early_operation／scaling |
| target_platform_codes | string[] | 意向经营的平台；尚未实际经营也可存在 |
| active_platform_codes | string[] | 用户明确当前经营或有相应可信业务证据的平台；与目标平台可重叠 |
| source_type | enum | form／conversation／shop_event／manual_correction／derived_rule |
| source_ref | ID / null | 表单提交、会话消息或授权事件引用；不无限复制整段会话 |
| evidence_status | enum | user_reported／system_verified／inferred；不能仅凭一个置信度数值决定覆盖 |
| observed_at／effective_at | datetime | 信息获得时间与业务生效时间；处理过期事件时分别使用 |
| base_revision／new_revision | integer | 防止并发更新覆盖最新资料 |
| changed_fields | object[] | field、old_value、new_value、scope、reason |
| candidate_status | enum | pending／accepted／rejected／superseded；仅供候选项 |
| inference_rule_version | string / null | 若由规则推导阶段，保留所用规则版本 |
| event_id／dedupe_key | string | 同一授权或资料更新事件只处理一次 |
| notification_state | enum | pending／displayed／acknowledged／suppressed，按目标会话／页面记录，避免反复反馈 |
| invalidated_at／suppressed_at | datetime / null | 更正、忘记或拒绝记忆后阻止旧信息再次进入上下文 |

对基础需求文档的细化：目标平台和实际经营平台需要区分；经营阶段移入 business_context，而不是对整个账号强制单值。首屏仍可保持“平台＋阶段”的简洁选择，服务端转换成对应范围的数据。

## 6. 表单、会话和授权的统一写入流程

### 6.1 更新链路

事实输入 → 识别来源与业务范围 → 生成字段补丁 → 校验与冲突判断 → 按现有保存策略提交 → 数据库事务写入并递增 revision → 记录变化事件 → 更新推荐与运行时摘要 → 在合适位置反馈。

| 输入来源 | 谁负责识别 | 可以直接确认的内容 | 需要保留为候选的内容 |
| --- | --- | --- | --- |
| 用户确认的表单 | 表单和服务端校验 | 所提交字段及用户选择 | 未填字段不能自行补全 |
| 用户明确的经营陈述 | 模型提取，工具校验 | 明确意向、明确已开店、明确更正 | 仅凭语气或模糊措辞推断的规模、收入等 |
| 假设、示例、第三方资料 | 模型识别引用范围 | 通常仅本轮使用 | 不能直接变成当前用户的长期画像 |
| 平台授权成功事件 | 服务端事件处理器 | 授权有效、店铺和平台的真实标识 | 主营类目、卖家经验、经营规模等额外推断 |
| 店铺状态／经营数据 | 可信接口与受控规则 | 真实返回的店铺状态与指标 | 由指标推导的阶段需有业务规则与适用范围 |

当前 save_memory 属于带确认的写工具。设计新的结构化更新工具时需沿用平台既有保存策略；若产品希望明确事实自动更新，应在程序和工具权限中定义允许范围，不能只用提示词要求 AI 绕过现有确认机制。本文不新增一套反复弹窗的保存流程。

### 6.2 字段更新规则

| 情况 | 处理方式 |
| --- | --- |
| 新增目标平台 | 合并到意向列表，不删除已有经营平台 |
| 新增某平台经营范围 | 新建范围，不覆盖其他平台的阶段 |
| 用户明确纠正意向或经营阶段 | 优先处理当前范围的明确更正，保留修改证据 |
| 系统授权事实与用户描述不同 | 按字段处理；“已授权”和“尚未营业”可以同时为真 |
| 旧授权事件延迟到达 | 按平台侧事件版本／生效时间校验，不能覆盖新的撤销状态 |
| 同一消息／授权事件重试 | 相同 dedupe_key 不重复更新、不重复通知 |
| 用户未提及某个旧字段 | 不清空原值 |
| 用户要求不记住／忘记 | 按平台能力停用或清除，后续不从旧会话自动恢复 |
| 更新失败 | 不声称已经记住；可暂用于当前会话，正式画像版本不变 |

## 7. 两个业务示例的具体处理

### 7.1 随便看看后，说“我想开 TikTok 的店”

| 步骤 | 数据变化／行为 |
| --- | --- |
| 用户最初点击随便看看 | onboarding_status=skipped；profile_status=unknown；stage=unknown；正常进入通用会话 |
| 后续明确说想开 TikTok 店 | 提取 platform=tiktok_shop、intent=open_shop；在该范围生成 stage=preparing 补丁 |
| 保存时 | 不自动补站点、预算、类目和店铺；保留用户其他平台的现有信息 |
| 更新后 | profile_status=partial；无需重新弹整套 onboarding；只在当前开店任务中补必要信息 |
| USER.md | 由新 revision 自动生成“TikTok：筹备开店，目标市场待补充” |
| AI 反馈 | “了解，你准备开 TikTok 店。我们先确定目标市场；你更倾向哪个国家或地区？”资料实际保存成功后，才能补充“已更新你的经营方向” |

反例：“如果我以后想开 TikTok 店会怎样？”只是一种假设，不自动设为长期目标。若用户正在 Amazon 规模运营，新增 TikTok 筹备范围，不把账号整体降级成筹备。

### 7.2 后续出现店铺授权，但旧画像仍是筹备

| 步骤 | 数据变化／行为 |
| --- | --- |
| 授权回调成功 | 校验账号、平台事件和店铺归属，记录真实授权与店铺事实；不依赖模型自己发现回调 |
| 找到对应经营范围 | 更新 TikTok 范围的 connected_shop_ids／可用能力，不影响 Amazon 等其他范围 |
| 判断阶段是否需要变化 | 查看有效店铺是否已建立、是否为当前实际经营对象、是否存在“测试店／未营业”等更新声明 |
| 有明确开店完成事实 | 在“起步经营＝已开店并开始配置／上新”的定义下，可由受控规则从 preparing 更新为 early_operation；记录推导原因，不要求已有订单 |
| 只有授权，经营状态不明确 | 自动更新连接事实，将阶段变化保留为候选；继续使用已连接能力，并自然询问“这家店已经开始运营，还是先连接做开店准备？” |
| 用户明确确认已开店 | 接受候选，更新对应范围阶段为起步经营 |
| AI 感知 | 当前页收到连接与画像变化事件；下一轮会话读取最新 revision 和变化摘要 |
| AI 反馈 | 事实明确时：“你的 TikTok 店铺已连接，接下来可以准备首批商品并创建刊登草稿。”阶段变化明确且已保存时，再说明阶段已更新 |

**不建议设置“有授权店铺＝规模运营”。** 单个新店、测试店、代运营授权和已有稳定业务是不同事实。授权撤销也不意味着卖家退回筹备，可能只是连接过期或暂时解绑。

## 8. 核心文件设计

建议保留现有三文件结构，增加一份按业务场景加载的引导规则。真实用户数据独立于这些共享规则。

| 文件／上下文 | 属性 | 职责 | 何时加载 | 不承担什么 |
| --- | --- | --- | --- | --- |
| agents.md | 共享、稳定规则 | 通用助手定位、任务优先、能力边界、专业助手协作 | Main Agent 基础规则 | 不保存某用户的平台与店铺，不强制每次填问卷 |
| bootstrap.md | 共享、首次引导规则 | 初次介绍、表单／对话收集选择、跳过与直接进入会话 | 首次适当场景或用户主动重新引导 | 不负责以后持续更新，不因用户完成而全局删除 |
| user.md | 共享、持续画像规则 | 识别哪些可记忆、字段语义、来源范围、合并更正、保存策略、忘记 | 每轮基础规则 | 不是每个账号的真实 USER.md；不直接改共享文件存资料 |
| guidance.md（建议新增） | 共享、业务引导规则 | 根据阶段、范围、资料缺口和可用能力决定下一步 | 涉及经营咨询／任务时 | 不为通用问题强加开店流程，不定义虚构能力 |
| USER.md（逻辑投影） | 当前用户的数据 | 最新偏好、各平台阶段、目标、已知与待补信息、版本 | 运行时按账号生成，作为数据读取 | 不作为高权限系统规则，不双向无校验写入 |
| runtime-context | 程序生成的动态数据 | 当前画像、实际店铺连接、能力可用状态、最近变化、当前任务范围 | 每轮／必要工具执行前刷新 | 不替代授权校验，不把完整历史全部塞给模型 |

这些文件名和加载顺序是项目自身约定。新增 guidance.md 需要显式接入现有 load_main_persona／中间件，不是写入文件后框架就会自动加载。

### 8.1 agents.md 的核心要求

- 先判断用户当前想完成什么；通用写作、查询、文档等任务直接承接。
- 缺少画像不阻止可完成的普通任务。
- 只在当前经营任务需要时补问关键经营信息。
- 经营画像和授权权限分开；推荐专家不表示已切换或已经执行。

### 8.2 bootstrap.md 的核心要求

- 首屏是收集面板时，不再同时输出一份重复问卷。
- 用户选择随便看看／其他，就进入独立会话，不反复追问完整身份。
- 首次引导状态与画像完整度分开判断；已跳过不表示以后禁止补充。
- 用户主动提出明确任务，优先承接任务，不先完成全部 onboarding。

### 8.3 user.md 的持续更新规则

- 每轮检查本轮是否出现明确的新事实、更正或长期偏好；没有变化就不写记忆。
- 区分“我准备做”与“如果做”，区分当前用户事实与引用资料。
- 生成最小字段补丁，带来源消息和适用业务范围；由工具完成校验与保存。
- 合并新增平台，不覆盖其他平台；用户更正时更新对应字段。
- 店铺授权事实以可信服务为准；经营阶段按明确声明或受控业务规则更新。
- 只有写入成功才告知已记录；拒绝或遗忘的信息不从历史重建。

### 8.4 guidance.md 的引导规则

| 场景 | 下一步引导 |
| --- | --- |
| unknown＋随便看看 | 通用助手直接接任务，不继续弹问卷 |
| preparing＋目标平台明确、市场未知 | 在当前任务中帮助选目标市场，再梳理开店清单 |
| preparing＋明确开店目标 | 推荐该平台专家、开店准备、选品或商机探索 |
| early_operation＋没有商品 | 引导商品导入、货源或选品 |
| early_operation＋已有商品、店铺未连接 | 可以先维护商品和刊登草稿，真实提交前再连接店铺 |
| early_operation＋商品和店铺可用 | 引导首批上新与刊登核对 |
| scaling＋有可用经营数据 | 引导经营诊断、批量任务和复盘；不虚构指标 |
| scaling＋缺少经营数据 | 提供连接或上传入口，也允许用户直接提供数据 |
| 用户只问通用问题 | 完成通用任务，不插入电商画像采集 |

## 9. USER.md 摘要示例

以下为建议的按用户生成的数据摘要格式，不是新的共享提示词。

```markdown
# 当前用户画像
profile_revision: 12
onboarding_status: skipped
profile_status: partial

## 沟通偏好
- 语言：中文
- 风格：简洁，先给行动建议（用户明确提供）

## 经营范围
### TikTok Shop
- 阶段：筹备开店（来源：用户明确表示计划开店）
- 目标市场：待补充
- 已连接店铺：1 家（来源：平台授权事件）
- 当前经营状态：待核对，连接成功不代表已开始运营

## 最近变化
- 新连接 TikTok 店铺，可继续准备商品与刊登草稿。
- 阶段是否进入起步经营：待明确开店状态。
```

一份摘要可以同时包含“筹备”和“有连接”，这不一定矛盾；它明确指出阶段仍待核对。确认开店后只更新 TikTok 范围，不改写其他业务。

## 10. AI 如何感知变化

仅修改 USER.md 或数据库，不会自动让正在运行的 Agent 获得新状态；需要程序负责刷新上下文。

| 时机 | 建议机制 | 用户体验 |
| --- | --- | --- |
| 表单保存后 | 返回新 revision；失效首页推荐缓存 | 首页即时刷新匹配内容 |
| 会话保存画像后 | 工具返回新版本与变化字段；后续推理使用新值 | 当前会话知道保存结果，不再使用旧字段 |
| 店铺授权回调后 | 写入连接事实与变化事件；按规则更新画像或候选 | 当前页显示已连接，可继续原任务 |
| 下一轮对话开始 | 读取最新画像、实际连接与必要变化摘要 | 老用户不必重新介绍经营状态 |
| 当前 Agent 正在执行 | 在下一安全边界读取变化；已确认任务参数使用原快照 | 不因后台画像变化偷偷改目标店铺或已确认发布范围 |
| 用户暂不在线 | 保存待展示变化，不要求发起后台模型对话 | 下次进入时集中提示有价值变化，不重复推送 |
| 相同变化已反馈 | 按事件及展示范围去重 | 不在每个新会话反复说“发现你连了店铺” |

店铺授权事件应由服务端消费；不能靠大模型持续轮询页面或等用户再次主动描述。生产可以使用事务事件／outbox 保证事实提交和事件投递可靠性，具体机制按现有基础设施选择。

## 11. 实施顺序与验收

| 顺序 | 要做的功能 | 验收重点 |
| --- | --- | --- |
| 1 | 统一字段、阶段文案及业务范围 | 随便看看不写死业务阶段；单账号多平台不互相覆盖 |
| 2 | 画像服务与最小更新工具 | 表单和对话更新同一份数据；草稿和已确认值分开 |
| 3 | USER.md 动态摘要与轮次刷新 | 运行时读取最新版本；共享规则不混入真实账号资料 |
| 4 | 授权事件接入与变化判断 | 连接事实自动更新；阶段有依据才升级；重复事件不重复处理 |
| 5 | guidance.md 与首页推荐接入 | 通用任务不被打断，不同业务阶段有不同引导 |
| 6 | 更正、忘记、多端冲突和恢复 | 不从旧会话复活已删除画像；多端不覆盖新版本 |

关键测试：

- 新用户跳过后，普通写作／查询正常进行，不重复询问身份。
- 后续明确计划开 TikTok 店，新增该平台筹备范围，记录来源，不凭空补国家。
- Amazon 已规模运营、TikTok 刚筹备，两份阶段并存。
- 授权成功自动更新连接状态；测试授权或经营状态不明时不强制提升阶段。
- 明确已开店后进入起步经营，下一轮和首页均感知新版本。
- 授权失效不把经营阶段降为筹备；延迟事件不恢复已撤销授权。
- 文件摘要滞后时以数据库版本为准；不同账号不共享真实 USER.md。
- 已确认的刊登任务不因画像或连接变化而暗中更换目标店铺。
- 用户拒绝记忆或要求忘记后，不重新从历史推导并持久化同一信息。

## 12. 待确认决策

1. 阶段文案是否采用“起步经营”，以及是否将第四入口改为“随便看看”。
2. 起步经营的最低业务定义是否为“真实店铺已建立并开始准备上新”，还是需要更强的经营证据。
3. 对话中明确事实的保存策略：沿用现有工具确认，还是由产品定义范围受限的自动更新策略。
4. 首期经营范围是否支持“平台＋市场”，还是先实现每平台一个范围。
5. 本轮是否需要物理 USER.md，或只需在运行时提供同等内容的数据投影。
