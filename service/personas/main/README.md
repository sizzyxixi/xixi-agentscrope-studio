更新日期：2026-10-23。

## 一、四份核心文件

| 文件 | 唯一职责 | 当前加载方式 |
| --- | --- | --- |
| [agents.md](./agents.md) | 通用助手身份、服务职责、专业协作与必要执行边界 | Main 的基础系统规则，全文读取 |
| [user.md](./user.md) | 持续识别资料、业务范围、合并更正、按真实工具保存与忘记 | Main 的基础系统规则，老用户也持续使用 |

真实用户资料不写入这些共享文件。每用户 USER.md 如需提供，应由账号主数据生成，作为参考数据使用；本次没有新建任何用户的真实 USER.md，也没有迁移画像数据库。

## 三、真实加载链路

`service/runtime.py` 的 `MAIN_PERSONA_FILES` 明确列出文件；不是 AgentScope 自动扫描或自动识别文件名。

- `load_main_persona()` 默认按 agents.md → user.md → guidance.md 全文组装。
- bootstrap.md 默认不读；首次轮次由 BootstrapMiddleware 通过系统提示词中间件加入。
- `include_bootstrap=True` 用于明确需要完整四文件的调用／检查，不在普通老用户轮次调用。
- 自定义智能体使用自己的角色正文，不混入 Main 的四文件；平台统一调度／建议等中间件契约不因此改变。
- 必需文件缺失、为空或编码错误时，停止创建 Main，向用户返回通用配置错误，不回显内部路径。
- 技能目录、工具 schema、调度、文件及记忆的真实调用说明继续由当前运行时提供，不在这些文件再写一份接口教程。
- 本次没有引入一次额外模型调用来分类场景；guidance.md 作为紧凑规则常驻，仅要求相关经营任务采用它。

基础规则在 Agent 创建时装配；已有缓存 Agent 不因文件变化自动重建，不能为了更新规则销毁正在等待审批的 Agent。新建并绑定当前正文的 Main 会话使用新规则；既有会话可能保留 agent_prompt 历史快照，重启进程或重建 Agent 也不保证替换该快照。生产热更新若有需要，应独立设计版本与安全切换。

## 四、onboarding：Agent 规则与程序职责

| 事项 | Agent 负责 | 程序负责／现状 |
| --- | --- | --- |
| 收集面板与输入框 | 不重复已明确由面板收集的问题 | 前端控制面板、输入框和页面跳转 |
| 首次对话引导 | 任务优先、一次只问必要问题 | 运行时按账号判断是否加载 bootstrap |
| 表单已经确认 | 使用实际提供的字段，避免重复问 | 前端画像目前是本地 Demo，正式共享需接入统一画像服务 |
| 随便看看／其他 | 正常服务，不强迫问卷，不记录成“新手卖家” | 前端直接新建会话；完整 skipped 状态仍需后端持久化 |
| 以后用户主动提到开店 | 使用 user.md 识别和保存明确增量 | 按工具权限、账号和字段范围校验 |
| 店铺授权后变化 | 用可信新状态调整表达和下一步，不假称监控到事件 | 回调消费、事实更新、画像规则判断与推送目前尚未完整接通 |
| 多平台不同阶段 | 不将一个平台的新目标覆盖整个账号 | 当前记忆文本可表达，结构化业务范围与版本仍待接入 |
| 老用户进入 | 承接目标，不重播全套首次引导 | 最新资料和必要变化要由程序按轮提供 |
| 关闭／完成／跳过引导 | 不把欢迎语、回复或确认点当作画像完整 | 当前 user_onboarding 仍只记录首次已引导标记，不是完整状态机 |
| 账号隔离、并发与授权 | 遵守已提供的资料和执行范围 | 始终由服务端检查；提示词不能代替权限与事务 |

### 当前首次判断保持不变

已登录、Main 普通对话、非后台／渠道任务、非审批恢复、账号尚无引导标记且没有启用的“MoonClaw 用户身份”时，程序按需加载首次引导。匿名调用不加载；已有有效身份的账号会被标记为已引导。

成功回复或展示工具确认会消费当前“已引导”标记；失败、取消和非正常中断保留重试机会。新会话、模型切换、服务重启、删除画像不会自动重置标记。这是既有技术行为，不代表用户已经完成或同意保存画像。

本次只重排核心规则和接通 guidance.md，不把这一个标记冒充为 not_seen／in_progress／completed／skipped 完整状态。完整状态、表单草稿、会话上下文和用户意愿应在后续后端接入时明确建模。

## 五、动态画像与当前保存适配

当前账号的启用记忆由 `ConsoleCapabilities.context()` 在普通对话轮次装配到 runtime-context，附带资源 ID；已有机制提供的同一资料不另行重复注入。审批恢复继续使用原轮次与原确认点。

当前持久化适配为“MoonClaw 用户身份”记忆资源。Main 增加带确认的 save_user_profile(content)，由服务端固定名称并查找当前账号原记录；没有该工具时仍可按精确名称及原 ID 使用 save_memory。数据库产品由 StudioStore 配置决定；尚未增加结构化画像字段、自动授权事件消费或物理 USER.md 双向同步。

专用工具拒绝自动恢复停用资料，也不在同名多记录间猜选；不会迁移名称不同的历史记忆。当前存储锁只保证同一进程内创建／更新串行，不代替多服务实例的唯一约束、版本检查或文本合并事务。后续结构化画像服务仍需补这些能力。

未来统一画像服务应提供字段范围、来源、版本与变化摘要；当前文件已经规定有此数据时如何使用，没有此能力时如何诚实处理，不能据此宣称这些服务已经实现。字段名和接口以真实 schema 为准，不以提示词里的业务术语虚构 API。

忘记和停用仍需实际管理工具；Main 当前没有该工具时说明未执行并指向真实入口。不能从历史重新生成用户拒绝或要求忘记的资料。

## 六、回归场景

以下为语义验收目标，静态文件和装配测试不能替代真实模型验收。

| 场景 | 应有行为 |
| --- | --- |
| “帮我翻译这段文案”但画像为空 | 完成翻译，不先问经营阶段 |
| 新用户只说“你好” | 简短介绍并问一个目标问题，不默认 TikTok |
| 表单已收集 Shopee 和市场 | 承接本轮需求，不再重问同一字段 |
| 用户选择随便看看后问普通问题 | 正常处理，不反复采集身份 |
| 后续说“我想开 TikTok 店” | 识别该平台筹备意向，按当前保存机制更新，只补当前需要的信息 |
| “如果以后开 TikTok 店会怎样” | 作为假设分析，不自动形成长期经营目标 |
| Amazon 规模运营，TikTok 新筹备 | 两个范围并存，不整体覆盖或降级 |
| 仅新授权一个 TikTok 店铺 | 说明连接带来的下一步；不等同已营业／规模运营 |
| 平台给出阶段更新成功 | 使用新阶段，必要时反馈变化 |
| 授权失效 | 引导连接恢复，不自动把经营阶段改为筹备 |
| 商品在非领星的 ERP | 先识别系统，再提供真实连接入口或咨询 |
| 用户只有商品而没授权店铺 | 可准备商品和草稿，真实提交前再授权 |
| 用户问公司或收费 | 查阅有效官方资料，不编造企业信息和账号权益 |
| 用户停止、致谢或请求已交付 | 不机械追加业务推荐 |
| 用户要求忘记资料 | 按实际工具执行，失败不称成功，不从旧历史恢复 |

## 七、验证边界

需验证默认 Main 三份常驻正文均加载、bootstrap 条件注入且只处理首次状态、老用户不依赖首次文件、文件异常安全失败、账号状态跨重启隔离，以及自定义智能体不受 Main 规则覆盖。

核心文件不进入默认共享知识索引。公开业务知识仍可按既有知识机制查询；内部规则保护不能只靠提示词，仍需文件权限与输出控制。
